Instance · game

DynamicGO

A real-time zone-control game: two sides place anchors, hold territory, and try to encircle. The client is a web build; the simulation and server are C++. The agent factory from the generic workflow is instantiated here at maturity tier T2.

There is no unattended orchestrator in the repository. A person picks a role in the editor, or a coordinator prompt delegates. Specs, test plans, and code on disk are the shared state. Agents pass paths, not transcripts.

Public build (the certificate is self-signed until a domain is attached): project page · play. Source stays private.

What changed from the generic loop

The code machine is the generic one, with game names on the last gates. Creative work is still not a state. It is checked before SPEC_ACCEPTED.

Debug, blocked-by-dependency, and retry counters live on the coordinator. Thresholds route a failed review or a failed build back to the right specialist instead of restarting the feature from scratch.

Support roles stay single-purpose: a strategic agent for questions and modification zones, a profiler for preference signals, a workflow architect who does not write game code, and an infrastructure agent for deploy. Skipping the coordinator means the person invoking one specialist has to enforce the gates themselves.

Starting a feature

  1. Name the feature and attach it to an epic. Anchor the description in the project’s assumptions and existing specs.
  2. Run game design until the mechanic spec is accepted. Run lore, graphics, UX, or sound first if the feature touches them.
  3. Hand the coordinator the feature id, the epic, and the paths to those accepted specs.
  4. At playtest, play a match and answer GO or NO-GO. The coordinator is not allowed to mark the feature ready without GO.

Why T2

DynamicGO has stable creative gates and more than one surface (simulation, web client, server). That is the T2 bar: typed handoffs, a hierarchical design knowledge base, recommendations that carry a confidence, and an access matrix. A shared tool server and monthly routing review (T3) are optional, not required to ship a feature.
